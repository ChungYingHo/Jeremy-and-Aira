## HTTP 是無狀態的

**HTTP 是無狀態協定（stateless protocol）**——每一次請求對 server 來說都是獨立事件，server 認不出「這次請求」和「上次請求」是不是同一個人發的。

沒有額外機制的話，後果很直接：使用者每換一頁就得重新登入，購物車這種跨頁面的狀態也留不住。

為了補上「狀態」這塊，前後端發展出幾種機制：核心是 **Cookie** 與 **Session**，瀏覽器端的 **localStorage** 和 **sessionStorage** 則是後來的延伸。

## Cookie

Cookie 是 Netscape 工程師 Lou Montulli 在 1994 年發明的，是最早解決 HTTP 無狀態問題的方案。

Cookie 是瀏覽器保存的小段資料，可由伺服器透過 `Set-Cookie` 設定，也可在限制允許時由 JavaScript 設定。瀏覽器只會在網域、路徑、安全性、SameSite 與憑證模式等條件符合時附上 Cookie；內容若要代表身分，後端仍須驗證，不能相信任意 cookie 值。

### Cookie 的運作流程

1. 使用者登入，server 驗證帳密成功後，在 HTTP **response header** 寫入 `Set-Cookie`。
2. 瀏覽器收到後，自動把 cookie 儲存起來。
3. 之後符合該 cookie 範圍與瀏覽器政策的請求，才會在 **request header** 帶上 `Cookie`。
4. Server 讀取 cookie，識別使用者身份或取得需要的狀態資訊。

### Cookie 的屬性

| 屬性 | 說明 |
| :--- | :--- |
| `Expires` / `Max-Age` | 設定期限；兩者同時有時 `Max-Age` 優先。省略則為 session cookie，session restore 可能將它還原，不能把關閉瀏覽器當成可靠登出 |
| `Domain` | 省略時限目前主機；指定合法上層網域時可涵蓋子網域，不以 port 隔離 |
| `Path` | 控制哪些請求路徑會帶上 cookie，不是資料存取安全邊界 |
| `HttpOnly` | 設定後，JavaScript 無法透過 `document.cookie` 存取這個 cookie |
| `Secure` | 設定後，只有 HTTPS 連線才會傳送這個 cookie |
| `SameSite` | 控制跨站附帶條件，可設 `Strict`、`Lax`、`None`；`None` 也須有 `Secure`。site 與 origin 不是相同概念 |

:::danger
`HttpOnly` 限制 JavaScript 讀取 cookie，能降低 **XSS（Cross-Site Scripting）** 直接竊取憑證的風險，但不會防止 XSS 本身。

- XSS 的玩法：攻擊者把惡意 JavaScript 注入網頁，用 `document.cookie` 把使用者的 cookie 偷走，拿去假冒身份
- 設了 `HttpOnly`，`document.cookie` 讀不到該 cookie；但惡意同站腳本仍可能發出帶 cookie 的請求或讀取頁面資料
- `Secure` 則確保 cookie 只在 HTTPS 加密連線下傳送，不會在明文傳輸時被中間人攔走

登入相關的 cookie，一律 `HttpOnly` + `Secure`。
:::

### 前端需要操作 Cookie 嗎？

**大多數情況下不需要。** 登入驗證相關的 cookie 由後端設定與讀取，加上 `HttpOnly` 之後 JavaScript 也碰不到。

前端真的會碰 cookie 的情境不多：
- 紀錄語言偏好或主題設定（但這種需求現在更常用 `localStorage`）
- 第三方 SDK（廣告追蹤、analytics）自己寫入的 cookie

瀏覽器端用 `document.cookie` 讀寫 cookie（前提是該 cookie 沒設 `HttpOnly`）：

```js
// 非驗證用途的偏好範例：一小時後到期
document.cookie = 'username=Jeremy; Max-Age=3600; Path=/; SameSite=Lax'

// 只讀到目前文件可見、非 HttpOnly 的 cookie
console.log(document.cookie) // "username=Jeremy; theme=dark"

// 刪除 cookie（把 expires 設成過去的時間）
document.cookie = 'username=; expires=Thu, 01 Jan 1970 00:00:00 GMT; path=/'
```

:::info
`document.cookie` 讀出來是一整條字串，要自己 parse，用起來不太舒服。現代專案如果真的要操作 cookie，通常直接用 [js-cookie](https://github.com/js-cookie/js-cookie)。至於 `HttpOnly` cookie，JavaScript 讀不到，本來就是後端的職責。
:::

## Session

Session 解的也是 HTTP 無狀態問題，跟 cookie 最大的差別在：**session 資料存在 server 端，不是 client 端**。

### Session 的運作流程

1. 使用者登入，server 驗證成功後，在 server 的記憶體（或 Redis、資料庫）建立一筆 session 資料，並產生一個唯一的 **Session ID**。
2. Server 把這個 Session ID 透過 `Set-Cookie` 傳給瀏覽器（是的，Session ID 通常就是存在 cookie 裡）。
3. 之後每次請求，瀏覽器帶上這個 Session ID 的 cookie，server 就根據 Session ID 找到對應的 session 資料，藉此識別使用者。

所以 session 和 cookie 不是兩個互斥的東西——session 通常就是靠 cookie 來傳 Session ID。差別在於資料放哪：cookie 把資料放在 client，session 把資料留在 server，client 手上只有一把「鑰匙」（Session ID）。

登入後，server 回傳的實際 HTTP header 大致長這樣：

```http
HTTP/1.1 200 OK
Set-Cookie: connect.sid=s%3A7xT...abc; Path=/; HttpOnly; Secure; SameSite=Lax
```

後續請求瀏覽器會自動帶上：

```http
GET /profile HTTP/1.1
Cookie: connect.sid=s%3A7xT...abc
```

Express 搭配 `express-session` 的流程片段。`authenticate` 是**待實作的憑證驗證函式**，不是 Express 內建 API；此片段不構成完整登入系統：

```js
import express from 'express'
import session from 'express-session'

const app = express()
app.use(express.json())

if (!process.env.SESSION_SECRET) throw new Error('SESSION_SECRET is required')

app.use(session({
  secret: process.env.SESSION_SECRET,
  resave: false,
  saveUninitialized: false,
  cookie: { httpOnly: true, secure: true, sameSite: 'lax' },
}))

app.post('/login', async (req, res, next) => {
  try {
    const user = await authenticate(req.body)
    if (!user) return res.sendStatus(401)
    req.session.regenerate((err) => {
      if (err) return next(err)
      req.session.userId = user.id
      req.session.save((saveErr) => {
        if (saveErr) return next(saveErr)
        res.sendStatus(200)
      })
    })
  } catch (err) {
    next(err)
  }
})

app.get('/profile', (req, res) => {
  if (!req.session.userId) return res.sendStatus(401)
  res.json({ userId: req.session.userId })
})
```

這裡省略 HTTPS 啟動、CSRF 防護與正式 session store。`secure: true` 要求安全連線，若 TLS 終止在可信反向代理，須正確設定 Express 的 proxy 信任範圍；預設 `MemoryStore` 只適合開發，不適合正式多程序部署。登入後重建 Session ID 可降低 session fixation 風險，細節見 [express-session 官方文件](https://expressjs.com/en/resources/middleware/session/)。

### JWT 的運作流程

Server-side session 可用於 MPA，也可用於 SPA；多伺服器部署時，則須考慮狀態儲存與路由：

- **狀態集中在 server**：每個登入中的使用者都要在 server 維護一筆 session 資料，使用者一多，記憶體就吃緊
- **橫向擴展困難**：使用者登入時 session 建在 A server，下一個請求被路由到 B server，找不到 session，就被登出了
- 解法不是沒有——sticky session（固定路由到同一台 server）或共享 session store（如 Redis）——但都是額外的架構成本

**JWT（JSON Web Token）** 是傳遞 claims 的格式，可用於 token-based 驗證；簽章型 JWT 可在不逐次查 session store 的情況下驗證，但不代表整個系統不保存狀態，也不限定 SPA 必須用 JWT。

1. 使用者登入，server 驗證成功後產生 JWT token，裡面放使用者 ID、角色、有效時間等資訊，回傳給前端。
2. 前端存放 token，兩種主流做法：
    - **`HttpOnly` cookie**：瀏覽器自動管理，JavaScript 無法存取，安全性較高，但要處理 CSRF。
    - **記憶體**（框架 state/store）：完整重載頁面後通常消失，可搭配適當續期機制；能執行同站 JavaScript 的 XSS 仍可能取得 token 或代發請求，並非免疫。
3. 若 token 可由前端讀取，可放 `Authorization: Bearer <token>`；若存於 `HttpOnly` cookie，則由瀏覽器按 cookie 規則附帶，JavaScript 無法讀出後再塞進 header。
4. 後端須固定允許的演算法並驗證簽章／MAC、有效期限及所需 issuer、audience 等條件，再做授權判斷；撤銷與帳號狀態也可能要求查共享資料。詳見 [JWT 安全實務 RFC 8725](https://www.rfc-editor.org/rfc/rfc8725.html)。

:::info
常見的 JWS compact 簽章型 JWT 有三段 Base64url 以 `.` 串起來：`header.payload.signature`。JWT 也可採 JWE 加密格式，不能把所有 JWT 都視為這三段結構。
- **header**：說明這個 token 用的是什麼簽名演算法
- **payload**：實際儲存的資訊，例如使用者 ID、角色等（這段是可以被解碼讀取的，所以不要放密碼或任何敏感資料）
- **signature**：依演算法以共享密鑰做 MAC，或以私鑰簽章、公鑰驗證，保護內容完整性

所以 JWT 的安全性不在於「資料被隱藏了」，而在於「資料如果被竄改，簽名就會對不上，server 就會拒絕這個 token」。
:::

### Session vs. JWT 怎麼選

Session 有個特性是 server 可以**主動讓它失效**——只要把那筆 session 從記憶體或 Redis 刪掉，使用者馬上就被登出。
只做離線簽章驗證的 JWT，在到期前通常不會因為刪掉前端副本就失效。若需要提早撤銷，可採拒絕清單、token 版本、金鑰輪換等設計，代價是增加狀態或影響其他 token；短效 access token 只能縮短風險時間，不等於即時撤銷。

所以兩種方案各有取捨，沒有絕對的優劣：
- 若需要逐 session 的即時撤銷，server-side session store 提供直接的控制點。
- 若服務間需要驗證可攜的 claims，簽章 token 可能合適；仍須設計有效期、授權與撤銷，不由 MPA／SPA 的區分單獨決定。

## localStorage 與 sessionStorage

Cookie 容量有限，單筆通常約 4KB，實際限制依瀏覽器；符合附帶條件的 HTTP 請求還會帶上它，增加傳輸量。純前端狀態若不需要伺服器讀取，可考慮 Web Storage。

HTML5 帶來了 **Web Storage API**，提供兩個更現代的瀏覽器端儲存方案：`localStorage` 與 `sessionStorage`。
兩者的 API 幾乎一模一樣，差別只在**生命週期**與**範圍**。

### localStorage

`localStorage` 沒有內建到期時間，通常跨瀏覽器重啟保留；使用者清除、隱私模式或瀏覽器儲存政策仍可能使資料消失，不應把它當唯一可靠備份。
資料的範圍以 **origin（protocol + domain + port）** 為單位，同一個 origin 下的所有頁面都讀得到。

```js
localStorage.setItem('theme', 'dark')

const theme = localStorage.getItem('theme') // "dark"

localStorage.removeItem('theme')

localStorage.clear()
```

### sessionStorage

`sessionStorage` 的 API 跟 `localStorage` 完全相同，但生命週期只在**當前的瀏覽器分頁（tab）開著的期間**。
一般頁面重載仍會保留；分頁工作階段結束才清除，瀏覽器的恢復功能可能延續該工作階段。
同 origin 的不同頂層分頁不會持續共享同一份資料；由 opener 開的新分頁可能取得初始副本，之後各自獨立。

```js
sessionStorage.setItem('step', '2')
const step = sessionStorage.getItem('step') // "2"
sessionStorage.removeItem('step')
```

### localStorage vs. sessionStorage vs. Cookie 比較

| 特性 | Cookie | localStorage | sessionStorage |
| :--- | :--- | :--- | :--- |
| 容量上限 | 單筆通常約 4KB，依瀏覽器 | 配額依瀏覽器與政策，常為數 MB | 配額依瀏覽器與政策，常為數 MB |
| 生命週期 | 到期或 session／清除政策 | 無內建期限，仍可能被清除 | 分頁工作階段，可受恢復機制影響 |
| 跨分頁共享 | 符合 domain／path 等範圍可共用，不以 port 隔離 | 同 origin 通常共享；嵌入情境可能分割 | 不持續共享，可能有 opener 初始副本 |
| 隨 HTTP 請求傳送 | 符合範圍、憑證模式與政策才附帶 | 否 | 否 |
| JavaScript 可讀 | 可（除非 HttpOnly） | 是 | 是 |
| 伺服器可設定 | 是 | 否 | 否 |

:::danger
**不要把 JWT 或任何 authentication token 存在 `localStorage`！**

這是一個相當常見的誤區，尤其是網路上有很多教學直接示範把 JWT 塞進 `localStorage`，然後每次 request 再從裡面拿出來放進 header 帶走。
問題在於，`localStorage` 可被同 origin 的頁面腳本存取；若有 XSS，攻擊者可能竊取 token 並以其權限發請求。只做離線驗證且沒有撤銷機制的 JWT，也較難即時停用被盜 token。

相對安全的做法是把 JWT 存在設有 `HttpOnly` 的 cookie 裡，讓 JavaScript 碰不到它，由瀏覽器自動附上，由後端讀取驗證。
當然，用 cookie 傳遞 token 又要注意另一種攻擊：**CSRF (Cross-Site Request Forgery)**，也就是惡意網站誘騙瀏覽器發出帶有你 cookie 的請求。
應對 CSRF 通常搭配 `SameSite` cookie 屬性或 CSRF token 機制來處理。

說到底，Web 安全沒有銀彈，每種方案都有自己的攻擊面，重點是要清楚知道自己在用什麼、它保護了什麼、又暴露了什麼。
:::

### localStorage 適合存什麼？

`localStorage` 和 `sessionStorage` 因為 JavaScript 可以直接讀寫，非常適合用來存放**不含敏感資訊的 UI 狀態**，例如：
- 使用者的外觀偏好（深色/淺色主題）
- 語言設定
- 表單的暫存草稿
- 使用者非敏感的個人設定

說白了，就是「放這裡被偷走也沒什麼大不了」的東西。

## Summary

一個簡單的場景比喻，幫助記憶這幾個概念的差異：

想像你去一家餐廳：
- **Cookie** 就像餐廳給你一張會員卡，每次來都帶著，服務生一掃就知道你是誰（資料可能直接寫在卡上，或只是一個 ID）。
- **Session** 就像餐廳只給你一個號碼牌，你的點餐記錄、座位偏好全都存在餐廳後台，號碼牌只是讓服務生查資料用的。
- **localStorage** 就像你手機裡記的備忘錄，下次來餐廳前可以先查一下自己上次喜歡吃什麼，但餐廳本身不知道也不負責這份備忘錄。
- **sessionStorage** 就像這頓飯吃完的點菜記錄，離開餐廳就清空了。

### 後端怎麼把憑證交給前端？

這個問題很多新手沒有搞清楚，常常以為「登入 API 回來就是登入完成」，但其實憑證（cookie、session ID、JWT）是透過**不同的管道**傳遞的，而不是都塞在 API 的 response body 裡。

| 機制 | 後端怎麼傳 | 前端怎麼收 |
| :--- | :--- | :--- |
| **Cookie** | response header 的 `Set-Cookie` | 瀏覽器自動存入，前端完全不介入 |
| **Session ID** | 同上，本質還是 `Set-Cookie` | 同上，瀏覽器自動處理 |
| **JWT（cookie 方式）** | response header 的 `Set-Cookie`（含 `HttpOnly`） | 瀏覽器自動存入，前端完全不介入 |
| **JWT（body 方式）** | response body 的 JSON，例如 `{ token: "..." }` | 前端從 response body 裡撈出來，自己決定存哪 |

關鍵就在最後兩行：JWT 後端可以選擇兩種回傳方式，**行為完全不同**。
用 `Set-Cookie` 傳時，前端 JavaScript 不能直接讀取這個 response header；`HttpOnly` 內容也無法透過 `document.cookie` 讀取。但前端仍須配合請求的 credentials 模式、CORS 與 CSRF 設計，瀏覽器也可能拒收或不附帶第三方 cookie。
但如果後端選擇放在 response body 裡，前端就必須自己去讀取、自己決定存在哪（記憶體、`localStorage` 等），也要自己在之後的請求手動帶上 `Authorization` header。

所以當你跟後端討論驗證機制時，要確認的不只是「我們用 JWT 還是 session」，還要確認「JWT 是從 header 來還是 body 來」——這直接決定了前端要不要自己處理存取邏輯。

### 現代實務怎麼用？

**登入驗證**：先確認身分協定、session／token 的生命週期與傳輸方式，再決定儲存位置。Cookie session 與 JWT 都可用在前後端分離的專案；不用未附統計的「主流」判斷取代需求分析。

**前後端共同處理驗證流程**：後端設定 `HttpOnly` 憑證，前端通常不直接讀寫它；前端仍需處理登入狀態、401、跨 origin 請求與 CSRF token。讀不到憑證不代表不需要理解流程。

**UI 狀態的儲存**：深色模式、語言偏好、側欄展開收合等非敏感狀態可放 `localStorage`；若 SSR 首次回應也需要讀取偏好，cookie 也可能合適。Web Storage 只保存字串，讀寫可能因配額或政策失敗，必要時應捕捉錯誤並提供預設值。
如果是多步驟表單的暫存進度、或只需要在這次操作中保留的資料，則會考慮 `sessionStorage`。
